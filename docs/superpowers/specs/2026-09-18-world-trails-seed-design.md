# World trails seed design

Date: 2026-09-18. Status: implementation of the user-approved seed plan, with the source corrections below.

## Outcome and decisions

Replace the eight fictional M1 trails with 50 real routes: 42 day hikes followed by eight multi-day treks. Half Dome and Trolltunga are the first two entries and the stable identities used by tests. Keep the existing three-tile photo atlas, with lake/coast/waterfall at index 0, forest/valley/gorge at index 1, and mountain/ridge/desert at index 2. The photographs remain illustrative.

Ratings, review counts and all 50 review excerpts are authored sample data. Detail continues to label excerpts “Sample review”; none of the excerpts is attributed to a real visitor. Descriptions are distinct, two-sentence summaries with a practical route note. The existing Welcome disclosure remains applicable.

Regions use `Area, Country`. Yosemite National Park, USA is the largest region with three entries: Half Dome, Mist Trail to Nevada Fall and Upper Yosemite Fall Trail. Seed version 2 shipped a Nearby chip bound to `NEARBY_DEMO_REGION` (`Yosemite National Park, USA`, label `Yosemite`) as a named demo region, not a claim about device location; the design revision R2 addendum below retires that chip and constant, and region is now selected only through search text.

The finite “For you” order begins with globally recognized day hikes, rotating continents to put different landscapes on the first screen. The remaining day hikes follow in the approved order; positions 43–50 group the eight treks. There is no personalization, new sorting or pagination. Source-led difficulty corrections produce 27 hard, 18 moderate and 5 easy entries; there are 12 dog-friendly feature tags.

Distances are metric and rounded to 100 m. Return walks include both directions; point-to-point figures cover one direction. Day-hike durations are representative walking estimates within the researched ranges. Trek durations encode itinerary days as `days * 1440`, including overnight itinerary time rather than continuous moving time. `trailDuration` preserves all sub-day labels and displays days, followed by whole residual hours when present, for durations of at least 1,440 minutes.

## Catalog and persistence implementation

`WorldTrails.kt` owns the ordered `internal val worldTrails: List<Trail>` and a private named-argument helper. The helper converts kilometres to integer metres. IDs obey `[a-z0-9][a-z0-9-]{0,99}`. The retired `demoTrails` list is removed. Review backfill uses one file-level `worldTrails.associate { it.id to it.reviewExcerpt }`, so fresh reads can add the appropriate sample excerpt to older payloads without duplicated copy or a per-row map rebuild.

Reuse `backend_meta.seeded` as the applied catalog seed version: zero means unseeded, one means the retired eight-row seed, and `SEED_VERSION = 2L` means this catalog. No SQL schema or migration version changes. Reseeding deletes only `backend_trail`, inserts the 50 rows in fixture order, and updates the marker in the same backend transaction. Saved memberships, clients, receipts, backend configuration and authority counters remain intact. `M1Backend.reseeded` reports whether this construction performed that transaction.

The catalog database must also lose stale query and detail payloads before repository construction. An old query cached through Store6 can carry freshness metadata and remain visible with `CachedOrFetch`, so just changing the backend rows is insufficient. Clear `cache_row` transactionally before creating `RealTrailRepository`; an absent source-of-truth row causes a fetch even if bookkeeper metadata remains. This follows the pinned Store6 [freshness contract](https://github.com/matt-ramotar/Store6/blob/582edfe86e64ddc71312ecd20a1895fc3de37b52/core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/Freshness.kt). Its experimental [SQLDelight bookkeeper](https://github.com/matt-ramotar/Store6/blob/582edfe86e64ddc71312ecd20a1895fc3de37b52/sqldelight/src/commonMain/kotlin/org/mobilenativefoundation/store6/sqldelight/SqlDelightBookkeeper.kt) requires adapter setup before concurrent driver work; invalidation here precedes repository and observer construction.

Backend and catalog are separate databases. A process could stop after committing the backend reseed but before clearing catalog rows. To close that restart gap, the factory also uses the catalog database's otherwise unused `backend_meta.seeded` cell as its durable applied catalog version. Initialize the catalog metadata row, then clear cache rows and set the catalog marker in one catalog transaction whenever `backend.reseeded` is true **or** the catalog marker differs from `SEED_VERSION`. This repeats safely after interruption and does not alter the authoritative backend's counters or configuration. The markers remain database-local despite sharing the SQLDelight schema.

Saved memberships referring to retired fictional IDs are deliberately retained. Their details remain unavailable after a successful Explore fetch because the new catalog has no such IDs; Saved and Collection show the existing unavailable-details notice. Saved's “Try again” re-walks the cache. For memberships whose IDs do exist in the new catalog, the notice can clear after Explore repopulates those detail rows. A restored detail route for a retired ID shows the existing “Trail unavailable” state.

## Explore and duration behavior

Under seed version 2, Nearby set the shared Yosemite region constant and the caption “Nearby · Yosemite demo region” appeared only for that exact region; design revision R2 retires the chip (see the addendum), and a checkpointed region is cleared on restore. Under seed version 2 the chip compared against the lowercased constant, and Explore restoration discarded any checkpointed region other than that demo region so an old `alpine` checkpoint did not restore an empty catalog. Under design revision R2 every checkpointed region is cleared on restore, and other selectors are kept.

The query matcher still searches both name and region. Feature filters still use AND, region equality is still case-insensitive after normalization, and the 30 km slider endpoint still means no maximum. Multi-day treks remain searchable and visible without adding new filter semantics.

Duration formatting retains the exact existing outputs below one day. Required examples are `45 min`, `2 h 15 min`, `7 h 0 min`, `1 day`, `4 days`, and `4 days 6 h`. Days use singular/plural correctly; residual minutes below a whole hour are not displayed once the duration is at least one day.

## Verification and evidence boundaries

Automated checks cover catalog size and uniqueness, receiver-compatible IDs, sample excerpt uniqueness, valid metric fields, one-decimal sample ratings, photo bounds, exactly eight trailing multi-day treks, pinned first identities, and the unique `half dome` query. Yosemite must remain the largest region with its three exact entries (the seed-version-2 Nearby assertion becomes a region assertion under design revision R2). No US national-park row may carry DOG_FRIENDLY. Explore restoration tests verify that a checkpointed region is discarded without losing other selectors (under seed version 2 the normalized Yosemite region survived; design revision R2 clears every region); the guard runs for both navigation checkpoints and Compose saveable snapshots.

The file-backed reseed test first populates catalog rows through a real Store6 observation so freshness metadata exists, saves a membership, closes drivers, rewrites backend catalog state to version one, and reopens. It checks that cache payloads are absent immediately after factory construction, a later observation returns 50 trails, and durable saved/receipt/counter evidence survives. A second interruption case covers a current backend marker paired with an old catalog marker. Existing persistence, review and fault tests use real seed identities; inert IDs in unrelated local fixtures need no change. Formatting has focused unit coverage.

The serialized verification targets are:

```bash
./gradlew :multiplatform:data:trail:impl:jvmTest :multiplatform:feat:savetrail:impl:jvmTest :multiplatform:screen:explore:impl:jvmTest :multiplatform:di:graph:active:jvmTest
./gradlew :apps:android:assembleDebug
```

Device acceptance is separate: update an existing eight-trail installation, confirm 50 trails and Half Dome first, search `yosemite` to see the three Yosemite entries, open a four-day trek, search `inca`, and inspect preserved Saved state. Verify a fresh installation independently. The Android accessibility instrumentation fixture now names Half Dome; changing its fixture is not itself evidence that it ran. Existing frozen `docs/evidence/m1` records describe older builds and remain untouched. Final execution results belong in the task report or a new evidence record; this design does not pre-claim passing builds or device behavior.

## Design revision R2 addendum (September 18, 2026)

Design revision R2 adds a fourth difficulty tier. The eight multi-day treks (positions 43–50) are seeded as `STRENUOUS` because they are overnight itineraries; the day hikes keep their source-led grades, so the catalog holds 5 easy, 16 moderate, 21 hard and 8 strenuous entries. Every route carries the derived activity `HIKING`; the eight treks also carry `BACKPACKING`. No highest-point or kid-friendly value is recorded because the sources above were not researched for them (DEV-30). The Nearby chip is retired: region is selected only through search text, and `NEARBY_DEMO_REGION` is removed. Seed versions 3 and 4 re-serialize these fields for existing installations; saved memberships, journals and receipts are preserved as before. Photographer credits appear on Trail detail and Welcome, not on cards.
